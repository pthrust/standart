|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| UC1 | Новый клиент (сайт) | Просмотр кредитных предложений | Клиент видит на сайте общие условия кредитов (ставка, сумма, срок) |
| UC2 | Новый клиент (сайт) | Подача заявки с ФИО и телефоном | Заявка сохраняется, клиенту приходит СМС о необходимости посетить отделение |
| UC3 |	Новый клиент (сайт) | Подача заявки с паспортными данными | Дополнительно заполняются паспортные данные. Система вызывает скоринг через БКИ, выдает предварительное решение |
| UC4 | Клиент ИБ | Просмотр персонализированных и предодобренных предложений | В ИБ отображаются кредиты с условиями, а также предодобренные предложения (ранее рассчитанный скоринг) |
| UC5 | Клиент ИБ | Подача заявки по предодобрению | Клиент выбирает предложение, указывает счёт зачисления, подтверждает СМС. Заявка отправляется в Кредитный конвейер |
| UC6 | Менеджер отделения | Продолжение работы с заявкой в АБС | Если клиент пришёл в отделение, менеджер находит заявку (по номеру) в АБС и продолжает оформление (в т.ч. подписание документов). Для новых клиентов – создание заявки в АБС вручную |
| UC7 | Менеджер кредитного отдела | Обработка заявок в Кредитном конвейере | Заявки из онлайн-каналов попадают в Кредитный конвейер. Менеджер изучает, вызывает скоринг (если не был вызван), принимает решение |
| UC8 | АБС | СМС-информирование клиента | Отправка СМС при изменении статуса заявки |

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | **Асинхронная обработка заявок** – избегать синхронных вызовов к АБС и Кредитному конвейеру для сохранения стабильности. |
| 2 | **Ускорение обработки предодобренных заявок** – срок реакции – в течение рабочего дня (не сутки). |
| 3 | **Минимизация нагрузки на систему скоринга** – не выполнять предрасчёты чаще, чем необходимо. |
| 4 | **Горизонтальное масштабирование новых компонентов** – микросервисы должны быть stateless. |
| 5 | **Безопасность** – TLS для всех внешних API, защита персональных данных. |
| 6 | **Технологическая совместимость** – использовать существующие стеки: Java (для микросервисов), Kafka (очереди), Oracle/PostgreSQL. |
| 7 | **Согласованность данных** – обеспечить eventual consistency между заявками на сайте, в АБС и Кредитном конвейере. |
| 8 | **Мониторинг и алертинг** – отслеживать глубину очередей, время ответа сервисов, ошибки. |

# Логика выбора технологий и архитектуры

**Создание отдельного микросервиса «Кредитный фронт» (Credit Front)** – он будет принимать заявки с сайта и ИБ, управлять предодобрениями и взаимодействовать с Кредитным конвейером асинхронно через Kafka. Это изолирует онлайн-каналы от монолита АБС и снижает нагрузку на Кредитный конвейер

**Синхронизация с Кредитным конвейером** – вместо пакетной загрузки раз в сутки внедряется Kafka Connect + Debezium для CDC (Change Data Capture) из АБС и прямой отправки заявок из микросервиса в очередь, которую Кредитный конвейер будет потреблять (через адаптер, реализующий REST или JMS). В перспективе можно доработать Кредитный конвейер для чтения из Kafka, но на первом этапе используется промежуточный адаптер

**Предодобрения** – хранятся в Redis в виде кеша с TTL. Обновляются при входе клиента в ИБ или по расписанию (например, раз в час), но не чаще, чтобы не перегружать скоринг. Для нового клиента на сайте предодобрение не вычисляется (только при заполнении паспортных данных вызывается скоринг через БКИ)

**Работа со скорингом** – микросервис вызывает систему скоринга только в случаях:
- новая заявка с паспортными данными (онлайн)
- повторная проверка по предодобренной заявке (упрощённый скоринг – возможно, только проверка изменений в БКИ без полного расчёта). Для упрощённого скоринга можно использовать сохранённый ранее результат с проверкой актуальности (например, данные БКИ не старше 7 дней)

**СМС-уведомления** – через существующий СМС-шлюз, вызываемый из микросервиса при изменении статуса

**Интеграция с АБС** – заявки, созданные в отделении (вручную), также должны попадать в Кредитный конвейер быстрее. Для этого в АБС добавляется триггер, который при создании/обновлении заявки отправляет событие в Kafka (или вызывает REST API микросервиса). Таким образом, заявки из отделения становятся доступны в Кредитном конвейере в реальном времени (а не раз в сутки)

**Обработка предодобрений в ИБ** – интернет-банк запрашивает предодобренные предложения через REST API микросервиса. Микросервис возвращает данные из Redis (если есть) или инициирует фоновый расчёт (но асинхронно, чтобы не блокировать пользователя)

### **Альтернативы**

| Альтернатива | Описание | Причина отклонения |
|---|---|---|
| Расширение монолита ИБ для кредитов | Добавление логики кредитования в существующий ASP.NET MVC | Зависимость от подрядчика, сложность масштабирования, риск для стабильности ИБ |
| Использование только пакетной загрузки (как сейчас) | Оставить ночную синхронизацию, не менять процесс | Не удовлетворяет требованию обработки предодобрений в течение дня |
| Синхронный вызов Кредитного конвейера при подаче заявки | ИБ вызывает API Кредитного конвейера напрямую | Кредитный конвейер не рассчитан на высокую нагрузку, может стать узким местом |
| Хранение предодобрений в основной БД микросервиса | Использовать MS SQL для хранения предодобрений | Медленнее, чем Redis, к тому же увеличивает нагрузку на БД |
| Использование RabbitMQ вместо Kafka | Проще в настройке | Kafka выбрана как перспективная и масштабируемая и уже используется в депозитном решении |

**Недостатки, ограничения, риски**

| Риск / Ограничение | Описание | Меры по снижению |
|---|---|---|
| Перегрузка системы скоринга | Даже при упрощённых предрасчётах частые вызовы могут создать нагрузку | Использовать кеширование результатов (Redis) с TTL. Выполнять предрасчёты только при входе в ИБ (не чаще 1 раза в день на клиента) |
| Задержки в Кредитном конвейере | Конвейер пока не умеет принимать события в реальном времени. Адаптер может стать бутылочным горлышком | На первом этапе использовать адаптер с пулом потоков, а в будущем доработать Кредитный конвейер для прямого чтения из Kafka |
| Согласованность данных между АБС, Кредитным фронтом и Конвейером | Заявки могут создаваться в разных местах, возможны конфликты | Ввести единый идентификатор заявки (генерируется в Кредитном фронте) и использовать его как ключ для всех систем. Реализовать идемпотентность в адаптерах |
| Безопасность персональных данных | Передача паспортных данных через сайт и ИБ | Использовать TLS, маскировать данные в логах, хранить хеши для идентификации |
| Необходимость доработки АБС для CDC | В АБС нужно добавить триггеры для публикации событий | Команда АБС — внутренняя, доработка возможна. Необходимо оценить затраты и включить в план |
| Обучение команды работе с Kafka и новыми микросервисами | Недостаток опыта у некоторых команд | Провести тренинги, использовать стандартные паттерны, документировать API |
