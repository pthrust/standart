# FURPS+ описание

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| **F** | **Функциональные (Functionality** |              |
| F1  | **Депозиты:** Клиент (новый и существующий) видит список депозитов со ставками (на сайте – общие, в ИБ – персонализированные) | Базовый функционал для подачи заявки |
| F2  | **Депозиты:** Подача заявки новым клиентом с сайта по номеру телефона и ФИО | Точка входа для новых клиентов |
| F3  | **Депозиты:** Подача заявки клиентом в ИБ с выбором счета и суммы, подтверждение СМС-кодом | Критичный путь для существующих клиентов |
| F4  | **Кредиты:** Подача заявки на сайте с номером телефона и ФИО (без паспорта – звонок, с паспортом – скоринг и решение) | Разделение потоков в зависимости от полноты данных |
| F5  | **Кредиты:** Интеграция с системой скоринга для получения решения по новой заявке (через БКИ) | Ключевая бизнес-логика. Требует API-шлюза для изоляции нагрузки |
| F6  | **Кредиты:** Отображение предодобренных предложений в ИБ на основе ранее рассчитанного скоринга | Требует хранения истории скорингов и синхронизации с Кредитным конвейером |
| F7  | **Общее:** Синхронизация статусов заявок между сайтом, ИБ, Кредитным конвейером и АБС (ручная обработка в бэк-офисе) | Необходим механизм eventual consistency |
|     |                                    |              |
| **U**   | **Удобство использования (Usability)** |              |
| U1 | Отклик системы на действия пользователя должен составлять миллисекунды (исправление проблем с загрузкой справочников) | Требует оптимизации кэширования и производительности БД |
| U2 | Соблюдение корпоративной системы дизайна (брендированные элементы, цвета) | Стандартное требование для всех фронтенд-систем |
| U3 | Интуитивно понятный интерфейс подачи заявки (минимум полей для нового клиента) | Влияет на конверсию, но не на архитектуру |
|     |                                    |              |
| **R**   | **Надёжность (Reliability)**           |              |
| R1 | Доступность сервисов 24/7, 99.9% времени (круглосуточно) | Сложно достижимо при текущей архитектуре (один ЦОД) и требует внедрения резервирования |
| R2 | Исключение прямой нагрузки на АБС при онлайн-подаче заявок (из-за перегруженности БД АБС) | **Критично.** Для этого необходим промежуточный слой (шлюз/брокер) и асинхронная выгрузка заявок в АБС |
| R3 | Отказоустойчивость ИБ: работа при сбоях в ЦОД, переключение на резервный ЦОД | Требуется географически распределенная архитектура или активный standby |
|     |                                    |              |
| **P**   | **Производительность (Performance)**   |              |
| P1 | Горизонтальное масштабирование и балансировка запросов между серверами/приложениями/ЦОД | Противоречит вертикальному масштабированию АБС. Необходим stateless дизайн для ИБ и уровня интеграции |
| P2 | Ускорение обработки заявок по предодобрению в течение того же дня | Требует перехода от пакетного обмена (раз в сутки) к потоковой или частой синхронизации (например, через Change Data Capture) |
| P3 | Обработка справочных данных менее чем за 1 секунду (исправление текущей проблемы) | Внедрение кэширования (Redis) или оптимизация запросов к MS SQL/Oracle |
|     |                                    |              |
| **S**   | **Поддерживаемость (Supportability)**  |              |
| S1 | Максимальное использование существующих технологий (MS SQL, Oracle) и платформ | Снижает стоимость владения и риски внедрения |
| S2 | Для очередей сообщений использовать Kafka (перспективно), но совместимость с текущей версией ИБ ограничена | **Важно:** Либо апгрейд ИБ, либо использование другого брокера (RabbitMQ) как компромисс |
| S3 | Наличие экспертизы внутри банка по новым технологиям (языки программирования) | Ограничивает выбор стека (Java/.NET/Python, т.к. они распространены в банках) |
| S4 | Разработка документации для дальнейшего расширения системы (API Spec, Arch Design) | Архитектурно значимо для развития платформы |
|     |                                    |              |
| **+R**  | **+ Требования (Requirements)**       |              |
| **I**  | **Выполнение (Implementation)**       |              |
| I1 | Перевод ИБ на микросервисную архитектуру в рамках задачи открытия депозитов (изолированный сервис) | Позволит независимо обновлять функционал вкладов без влияния на другие модули ИБ |
| I2 | Избежать доработки ядра системы (СМС) силами подрядчика; реализовать бизнес-функционал силами команды банка | Влияет на план работ, но не на архитектуру (используем существующее ядро) |
| **O**  | **Операционная деятельность (Operations)**       |              |
| O1 | АБС масштабируется вертикально — необходимо буферизировать запросы из ИБ, чтобы не вызывать Lock-ов в БД АБС | Использовать паттерн "Transaction Outbox" или очередь для асинхронной записи заявок в АБС |
| O2 | Мониторинг и алертинг: отслеживание глубины очередей (Kafka), времени ответа сервисов и ошибок интеграции | Без этого невозможно обеспечить 99.9% доступности. Внедрить централизованный логинг (ELK/Splunk) |
| O3 | Управление конфигурациями ставок через АБС вместо XLS-файлов (единый источник истины) | Текущее хранение в XLS — риски ошибок. Требует доработки АБС или создания админ-панели |
| **L**  | **Правовые и нормативные требования (Legal)**       |              |
| L1 | Шифрование трафика (TLS 1.3) и защита чувствительных данных (персональные данные) | Соответствие 152-ФЗ (РФ) и PCI DSS |
| L2 | Обязательная идентификация клиента в отделении для новых клиентов (офлайн) | Бизнес-правило, не влияет на архитектуру (просто изменение статуса заявки) |
| L3 | Согласие на обработку персональных данных и СМС-информирование (офферта) | Требуется реализация виджета согласий на фронтенде |
