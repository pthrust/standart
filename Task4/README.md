### **Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| UC1 | Сотрудник кол-центра банка | Консультация клиента по ставкам | Оператор видит в CRM актуальные ставки по депозитам, может озвучить их клиенту |
| UC2 | Сотрудник партнёрского кол-центра | Консультация клиента по ставкам | Внешний оператор получает файл с актуальными ставками и использует его для консультаций |
| UC3 | Менеджер (бэк-офис депозитов) | Публикация обновлённых ставок | При загрузке новых ставок в АБС система автоматически готовит файл для передачи |
| UC4 | АБС | Передача файла ставок партнёру | Автоматическая выгрузка файла в SFTP-каталог партнёрского кол-центра при изменении ставок |

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Актуальность данных – ставки должны передаваться в кол-центр не позднее чем через 15 минут после обновления в АБС |
| 2 | Доступность для кол-центра – информация о ставках должна быть доступна в CRM-системе кол-центра в режиме чтения |
| 3 | Файловый обмен с партнёром – передача ставок партнёрскому кол-центру осуществляется через SFTP в виде файлов |
| 4 | Безопасность – файлы с чувствительной информацией (ставки) должны передаваться по защищённому каналу (SFTP с аутентификацией) |
| 5 | Масштабируемость – решение должно выдерживать рост количества обращений в кол-центр |
| 6 | Надёжность – даже при сбоях в АБС кол-центр должен иметь доступ к последней актуальной версии ставок |

# Логика выбора технологий и архитектуры

**Хранение ставок в едином источнике** – все ставки по депозитам ведутся в АБС (загружаются из XLS-файлов через интерфейс Delphi). Это единственный источник

**Публикация ставок в Kafka** – при загрузке новой ставки в АБС срабатывает триггер (или процедура), которая отправляет событие в Kafka (тема deposit-rates)

**Микросервис «Депозиты» обновляет кеш** – он подписан на тему deposit-rates и обновляет Redis, чтобы сайт и ИБ всегда показывали актуальные ставки (это уже реализовано в Task 3)

**Сервис экспорта ставок для кол-центра** – новый компонент (или расширение микросервиса «Депозиты»), который:
- подписывается на тему deposit-rates
- при получении события формирует файл с актуальными ставками в согласованном формате (например, CSV)
- сохраняет файл в локальное хранилище (или в общую папку)
- обеспечивает доступ к этому файлу для CRM-системы кол-центра (например, через REST API или общую сетевую папку)

**Передача файла партнёрскому кол-центру** – отдельный адаптер-экспортёр (или тот же сервис) подписывается на тему deposit-rates и:
- генерирует файл в формате, ожидаемом партнёром (например, CSV с определёнными колонками)
- подписывает файл электронной подписью (опционально)
- загружает файл на SFTP-сервер партнёра (с использованием существующих учётных данных)
- логирует успешность загрузки и уведомляет администратора в случае ошибки

**Интеграция с CRM кол-центра** – CRM-система кол-центра (Java Spring Boot, PostgreSQL) может:
- либо читать файл из общей папки (если развёрнута в той же сети)
- либо обращаться к REST API микросервиса «Депозиты» для получения актуальных ставок (что предпочтительнее, т.к. даёт более свежие данные и не требует файлового обмена внутри банка)

### **Альтернативы**

| Альтернатива | Описание | Причина отклонения |
|---|---|---|
| CRM обращается напрямую к АБС за ставками | Прямой SQL-запрос к таблицам АБС | Создаёт дополнительную нагрузку на АБС, нарушает принцип изоляции |
| Ежедневная рассылка Excel-файла по email | Ручная отправка файла сотрудником бэк-офиса | Не гарантирует актуальность, зависит от человеческого фактора, не масштабируется |
| Партнёрский кол-центр получает ставки через API | REST API, предоставляемый банком | Партнёр не поддерживает API, только файловый обмен |
| Хранение ставок в отдельной БД (не в АБС) | Дублирование данных | Нарушает принцип единого источника истины, сложно поддерживать согласованность |
| Использование RabbitMQ вместо Kafka | Более простой брокер | Kafka уже выбрана для депозитного решения, к тому же унификация упрощает сопровождение |

**Недостатки, ограничения, риски**

| Риск / Ограничение | Описание | Меры по снижению |
|---|---|---|
| Задержка при передаче файла партнёру | SFTP-передача может занимать несколько минут, особенно при большом объёме | Для ставок задержка в 5–10 минут допустима; при необходимости можно уменьшить, генерируя файл чаще |
| Сбой SFTP-сервера партнёра | Если сервер недоступен, файл не будет доставлен | Реализовать повторные попытки с экспоненциальной задержкой, алертинг администратора |
| Изменение формата файла | Партнёр может запросить новый формат | Хранить конфигурацию формата отдельно, легко изменять без переделки всей логики |
| Безопасность | Файлы содержат коммерчески чувствительные ставки | Использовать SFTP с сильной аутентификацией, передавать файлы по защищённому каналу, подписывать файлы электронной подписью |
| Нагрузка на Kafka | При частом изменении ставок (например, несколько раз в день) растёт количество сообщений | Kafka хорошо справляется с такими нагрузками, ограничить частоту изменений ставок (не чаще 1 раза в час) |
| CRM получает ставки из разных источников | Если CRM будет одновременно читать из Redis и из файла, возможны расхождения | Использовать единый источник (Redis) через REST API, файл только для партнёра |
