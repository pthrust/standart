### **Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| UC1 | Новый клиент (сайт) | Просмотр списка депозитов | Клиент видит на сайте перечень доступных депозитов с общими ставками (загруженными из АБС через кеш) |
| UC2 | Новый клиент (сайт) | Подача заявки на депозит | Клиент заполняет ФИО и номер телефона, отправляет заявку. Заявка сохраняется, менеджер кол-центра связывается с клиентом |
| UC3 |	Клиент ИБ | Просмотр персонализированных ставок | В ИБ отображаются ставки, рассчитанные на основе суммы и срока (без учёта кредитного риска) |
| UC4 | Клиент ИБ | Подача заявки на депозит с подтверждением | Клиент выбирает счёт и сумму, отправляет заявку. Подтверждение осуществляется с использованием СМС-кодом |
| UC5 | Менеджер бэк-офиса/кол-центра | Обработка заявки в АБС | После звонка менеджер изучает заявку в АБС, при необходимости предлагает особые условия (согласование с кредитным отделом – вне MVP) |
| UC6 | Система | Отправка СМС-уведомлений | После подтверждения ставки и открытия депозита клиент получает СМС оповещение (через СМС-шлюз телеком-оператора) |
| UC7 | Сотрудники бэк-офиса депозитов | Управление ставками| Загрузка ставок из Excel в АБС через интерфейс АБС (Delphi). После загрузки АБС публикует событие об изменении |

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | **Производительность**: Отклик – миллисекунды, справочные данные < 1 с |
| 2 | **Доступность**: 24/7, 99.9% |
| 3 | **Надёжность**: Избегать синхронных обращений к АБС; использовать асинхронную передачу заявок через очередь |
| 4 | **Масштабируемость**: Горизонтальное масштабирование новых компонентов; АБС – вертикально |
| 5 | **Безопасность**: TLS, защита персональных данных |
| 6 | **Технологическая преемственность**: Использовать существующие БД (MS SQL, Oracle) и языки с имеющейся экспертизой (Java, .NET, Python) |
| 7 | **Разделение прав доступа**: Депозитный микросервис не имеет доступа к кредитным данным (АБС-кредиты, Кредитный конвейер, Скоринг) |
| 8 | **Избегание доработок ядра ИБ**: Функционал депозитов реализуется вне монолита ИБ |

# Логика выбора технологий и архитектуры

**Выделение микросервиса «Депозиты»** – чтобы не зависеть от подрядчика, обслуживающего ядро ИБ (ASP.NET MVC), и обеспечить независимое развертывание. Микросервис реализуется на Java Spring Boot, так как в банке есть экспертиза Java (команда АБС, кол-центр, кредитный конвейер). Это также упрощает интеграцию с Kafka (поддерживается Spring Cloud Stream) и Redis

**База данных микросервиса** – MS SQL, поскольку она уже используется в ИБ и есть соответствующие администраторы. Это упрощает операции резервирования и мониторинга

**Очередь сообщений** – Apache Kafka. Хотя текущая версия ИБ несовместима с Kafka, микросервис депозитов и адаптер к АБС работают с Kafka независимо, поэтому ограничение не критично. Kafka обеспечивает высокую пропускную способность, сохранность сообщений и возможность репликации для отказоустойчивости

**Кеширование ставок** – Redis (in-memory хранилище) для обеспечения миллисекундного отклика. Обновление кеша происходит по событиям от АБС

**Интеграция с АБС** – через адаптер (консюмер Kafka), написанный также на Java. Адаптер вызывает API АБС (Oracle PL/SQL – возможно, через REST-интерфейс, который нужно разработать, или через вызов хранимых процедур). Поскольку АБС разрабатывается внутри банка, мы можем добавить небольшой REST-сервис на основе Oracle ORDS или использовать прямое JDBC-соединение для вызова процедур. В MVP предпочтительнее создать простой REST-эндпоинт в АБС (на основе Oracle REST Data Services), чтобы не усложнять интеграцию

**Обновление ставок из АБС** – при загрузке Excel-файла через интерфейс АБС (Delphi) мы можем добавить триггер в БД Oracle, который при вставке/обновлении таблицы ставок отправляет HTTP-запрос в микросервис (или публикует сообщение в Kafka). Альтернативно – использовать Debezium (CDC) для захвата изменений, но для MVP проще реализовать вызов REST из хранимой процедуры (через UTL_HTTP)

**Интеграция с СМС** – через СМС-шлюз телеком-оператора. В банке есть IT-отдел, который поддерживает этот шлюз, предоставляя REST API или SOAP. Микросервис вызывает этот API для отправки кода подтверждения и уведомлений

**Фронтенды** – Сайт (PHP + React) и Интернет-банк (ASP.NET MVC) обращаются к REST API микросервиса по HTTPS. Для ИБ добавляются новые страницы, которые вызывают API микросервиса (без изменения ядра ИБ). Это возможно, так как ИБ – монолит, но мы можем добавить новый контроллер или использовать клиентский JavaScript для вызова внешнего API

### **Альтернативы**

| Альтернатива | Описание | Причина отклонения |
|---|---|---|
| Реализация функционала внутри монолита ИБ | Добавление контроллеров и логики в ASP.NET MVC. | Зависимость от подрядчика для обновления ядра, сложность масштабирования, риск влияния на другие модули |
| Использование RabbitMQ вместо Kafka | Более простой брокер, совместимый с .NET. | Kafka выбрана как перспективная, обеспечивает лучшее масштабирование и хранение сообщений; несовместимость с ИБ не критична |
| Прямой вызов АБС (синхронно) из микросервиса | Микросервис вызывает API АБС сразу при получении заявки. | Создаёт нагрузку на АБС, нарушает требование асинхронности; при сбоях АБС заявки теряются |
| Хранение ставок в БД микросервиса без Redis | Чтение из MS SQL. | Медленнее, чем in-memory, не гарантирует миллисекундный отклик при пиковых нагрузках |

**Недостатки, ограничения, риски**

| Риск / Ограничение | Описание | Меры по снижению |
|---|---|---|
| Ручной ввод ставок | Ставки загружаются из Excel вручную, возможны ошибки и задержки | В MVP допустимо, но в дальнейшем планируется автоматический расчёт на основе макропоказателей без доступа к кредитным данным |
| Отсутствие готового REST API в АБС | Для интеграции потребуется доработать АБС | Команда АБС разрабатывает систему внутри банка, поэтому доработка возможна. На этапе реализации MVP можно реализовать простой эндпоинт |
| Задержка синхронизации ставок | Обновление кеша происходит после загрузки в АБС и может занять несколько секунд | Для MVP приемлемо, но можно сократить до миллисекунд через триггеры |
| Kafka требует дополнительного администрирования | Команде придется освоить Kafka | В банке есть экспертиза по Java. Kafka настраивается стандартно. Скорее всего потребуется привлечь консультантов на этапе внедрения |
| Разделение доступа | Микросервис не может использовать кредитные данные, что ограничивает персонализацию | Для MVP персонализация по сумме/сроку достаточна. Особые условия – ручное согласование и пока вне MVP | 
| Доступность 99.9% | Текущий ИБ и АБС не обеспечивают такой уровень | Микросервис проектируется отказоустойчивым. Для АБС используется резервный ЦОД, но переключение пока ручное |
